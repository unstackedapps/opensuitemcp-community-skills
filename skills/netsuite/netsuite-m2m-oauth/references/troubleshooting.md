# Troubleshooting NetSuite M2M OAuth

When setup fails, identify the failing boundary before changing configuration.

## A. Integration Record is unavailable during M2M mapping

Check:

- Client Credentials (Machine to Machine) Grant is enabled
- the required OAuth scope is enabled
- the user performing setup has permission to manage OAuth applications/mappings

## B. JWT cannot be created locally

Check:

- private-key path and format
- JWT library support for the selected algorithm
- EC versus RSA key type
- file permissions
- encrypted-key handling in the selected runtime

Do not weaken key handling just to make the library accept the file.

## C. Token endpoint rejects the assertion

Inspect the non-secret JWT claims and mapping in this order:

1. `aud` exactly equals the endpoint being called
2. `iss` matches the Integration Record Client ID
3. `kid` matches the Certificate ID from the mapping
4. `alg` matches the uploaded certificate/private key pair
5. scope is enabled on the Integration Record
6. `iat` and `exp` are valid Unix seconds
7. system clock is accurate
8. certificate is not expired or revoked
9. uploaded public certificate matches the private key used for signing
10. application/entity/role/certificate mapping is the intended one

Use NetSuite's OAuth/Login Audit Trail when available rather than guessing from a generic `invalid_grant` response.

## D. Token succeeds but resource request returns 401/403

Authentication and authorization are separate stages.

Check:

- Bearer token is being sent to the correct account-specific resource domain
- requested service matches the granted scope
- mapped role has the required service permission
- mapped role has the required record/data permissions
- RESTlet deployment/audience permits the mapped role when applicable

Do not respond to a permissions failure by automatically switching to Administrator.

## E. Works in production but not sandbox/Release Preview

NetSuite M2M client-credentials mappings are environment-specific. They are not copied from production to sandbox or Release Preview, and sandbox refreshes clear the setup.

Recreate the mapping and certificate configuration for the target environment and use that environment's account-specific URLs.

## Common mistakes

### "Where is my permanent token?"

There is no permanent M2M access token.

The durable trust is the configured mapping plus certificate/key pair. The application repeatedly proves possession of the private key with a short-lived JWT client assertion and receives a short-lived access token.

### "Is the JWT the access token?"

No.

The application creates and signs the **client assertion JWT**. NetSuite validates it and returns a separate **access token**.

### "Do I upload private.pem to NetSuite?"

No.

Upload only the public certificate. The private key stays with the client application.

### "What is kid?"

`kid` is the **Certificate ID generated by the NetSuite M2M mapping**, not the certificate filename and not the Client ID.

### "What is iss?"

`iss` is the **Client ID from the Integration Record**.

### "Why does the role matter if the certificate authenticated me?"

The certificate proves which configured client identity is connecting. The mapped role determines what that identity is allowed to do after authentication.

### "Can I use this for the NetSuite AI Connector Service?"

Do not assume so. NetSuite's current Integration Record rules require Client Credentials/M2M to be cleared when the AI Connector Service scope is used. Route that case to the AI Connector authentication workflow.
